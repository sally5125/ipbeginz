## 1. 의도한 서비스 구조 vs 문서·프로토타입의 실제 구조

### 1-1. 구조 대조표

| 의도(제품 오너) | SPEC / 기획문서 | 프로토타입 코드 | 판정 |
|---|---|---|---|
| 계정 1개 → 프로젝트 프로필 N개 | SPEC L168~173, L305 명시 | `ACCOUNT` 단일(AD L106), `PROFILES` 8건에 **소유자 필드 없음**(AD L123~141). 모든 프로필을 "내 것"으로 취급 | 데이터로는 암묵, 로직으로는 미구현 |
| 프로필 유형 IP / Brand / Creator | SPEC L303~311 확정 | 인코딩 6종 혼재(§3-1) | 개념 일치, 구현 불일치 |
| IP = IP 매매 또는 프랜차이즈 권한 부여 | IP판매(`dist`) + 사용권 판매(`license`) 캠페인 + 프랜차이즈 탭 라인 + 자동 라이선스 캠페인 + 맞춤 견적 + 사용권 상세 구매 | 각각 별도 상태·데이터. 프랜차이즈 탭 "프랜차이즈 추가" 모달은 저장·닫기 핸들러 미정의(10148) | **경로 5개가 서로 연결되지 않음** |
| 캠페인 유형 = 광고 캠페인 / IP 프랜차이즈 캠페인 | 이런 2분류 없음. EARN/SPEND × 세부 유형 12종(IP판매 · 사용권 판매 · 크리에이터 3종 / IP 구매 의뢰 · 사용권 신청 · 홍보 · PPL · 퀵오더 · 콜라보) | `ncSubType` 9종 + 레거시 `NC_KINDS` 4종 + `CAMPAIGNS.kind` 4종 | **분류 축이 다름**. "프랜차이즈 캠페인을 만든다"는 행위가 정의되지 않음 |
| **프로필 ≠ 캠페인. 프로젝트 프로필이 캠페인을 만든다** | SPEC L173 "캠페인은 반드시 프로필에 속합니다"는 일치. **그러나 SPEC L1120~1123(10-01)은 "크리에이터 프로필 저장 시 셀프 프로모션 캠페인 자동 생성 · 프로필이 곧 캠페인 · 캠페인 만들기를 요구하지 않음"으로 둘을 합쳐 버림** | 자동 생성 미구현. 대신 프로필 저장 후 `askOffers` 팝업 → 캠페인 만들기 이동(13686~13735) | ❌ **원칙 위반**. 크리에이터만 예외로 "프로필 = 캠페인"이 되어 개념 모델이 깨짐 |
| IP: 지출형 + 수익형 | SPEC L324 일치 | `ncSubAllowed` 일치 | ✅ 방향 일치 |
| Brand: 지출형만 | SPEC L325, L341 일치 | 일치 | ✅ (단 `ncBlank()` 기본 흐름이 수익형이라 브랜드 진입 시 차단 상태로 시작 → 자동 보정, 11981) |
| Creator: 수익형만 | SPEC L326, L330 일치 **그러나 L209 "크리에이터가 지출형 캠페인을 열 때만 예치금 필요"가 잔존** | 일치 | ✅ 방향 일치, 문서 내부 모순 |

### 1-2. 오너 2분류를 문서 체계에 매핑하면

```
광고 캠페인(SPEND)      = 홍보(마케팅) · PPL · 퀵오더 · 콜라보 모집      ← 발주자가 돈을 냄
IP 프랜차이즈 캠페인(EARN) = 사용권 판매(2nd License) · IP판매(Sale)      ← IP가 권리를 팜
   ?                     = IP 구매 의뢰 · 사용권 신청(브랜드 SPEND)       ← 권리를 "사겠다"는 공고. 어느 묶음에도 안 들어감
   ?                     = 크리에이터 셀프 프로모션(EARN)                ← 광고도 프랜차이즈도 아님
```

→ 오너의 2분류를 쓰려면 "권리 매수 공고"와 "크리에이터 서비스"의 자리를 먼저 정해야 함(§6-1 제안 참조).

### 3-3. 한 개념 여러 필드

- `CAMPAIGNS.kindLabel` vs `CAMPAIGN_META.subType` / `CAMPAIGN_META.owner` vs `PROFILES.type`(via ipId) / `registered·certified` vs `verified`
- 독점 · 기간: `CAMPAIGN_EXT.exclusive/term` vs `LICENSE_LINES.terms[1..2]` vs `CONTRACTS.terms` 문자열 — 같은 개념 3곳. `LICENSE_LINES.terms[2]`에 독점과 "러닝 8%"가 같은 슬롯(AD L297, L300)
- `LICENSE_LINES.ok` == (`state === '판매 중'`), `MKT_FIELDS` ≡ `CAT_MAJOR`(AD L280 주석이 인정)
- `PLANS`(IP 구독 티어 Fan/Creator/Studio) vs `PLATFORM_PLANS`(Free/Pro/Business/Enterprise) 혼용. SETTINGS "현재 플랜 Creator"가 IP 티어명을 플랫폼 요금제로 사용
- 금액: 문자열(`'₩12,000,000'`, `'판매액 18%'`) vs 숫자(`CAMPAIGN_META.budget`, `APPLICANTS.rate`, iframe KRW 정수) 혼재. 예산 · 예치금 필드가 `CAMPAIGNS`에 없음
- `CAMPAIGNS.ipId`가 브랜드 · 크리에이터 프로필도 가리키는 misnomer

## 5. UX 복잡도 — 쉽게 할 수 있는 걸 어렵게 만든 흐름 (요청 2)

### 5-1. 캠페인 만들기: 필수값 4개를 위해 13구획 · 100여 컨트롤

브랜드 → 홍보(마케팅) 캠페인 기준(가장 단순한 지출형):

- **게시에 실제 필요한 입력 4개**: 주최 프로필 확인 · 홍보 대상 텍스트(`ncSubject`) · 1인당 기준 금액 또는 고정 금액 · 게시 시작일(기본값 없음)
- **노출되는 것**: 13구획(기본 정보 · 섭외할 크리에이터 조건 · 지원 자격 · 선정 · 홍보 대상 · 조건 · 시딩 · 보상 · 모집 인원 · 예산 · 정산 · 권리 사용 범위 · 배포 자료 · 유의사항 · 게시 채널 · 일정 · 검수 · 최종 확인), 컨트롤 약 input 32 · select 15 · textarea 6 · button 110+
- **최소 상호작용 약 18~20회 + 모달 3개**: `+ 만들기` → 캠페인 → (브랜드는 수익형 기본값이 차단 상태로 뜬 뒤 자동 보정 1회 깜빡임) → 주최 프로필 피커 모달 → 지출형 카드 → 세부 유형 카드 → 목적 칩 → 홍보 대상 → 금액 → 시작일 → 스크롤 끝 게시 → 예치금 부족 토스트 → 충전 → 지갑(결제수단 · 금액 · 충전) → 돌아가기 → 다시 게시 → 광고 팝업 "다음에 하기"
- **검사하지 않는 것**: 제목(`ncTitle`은 상태에 있지만 `publishCampaign`이 검사하지 않음 — 빈 제목은 광고 팝업에서 '방금 만든 캠페인'으로 대체됨, 15888) · 소개 · 썸네일 · 마켓 분류 · 목적 · 모집 대상 · 노출 국가 → 제목 없는 캠페인 게시 가능. 반대로 중요하지 않은 시작일은 필수

중복 입력:
- 분류 5중: 흐름 → 세부 유형 → 목적 → 마켓 분류 대/소(6625, 6637) → 검색 키워드. 목적은 세부 유형에서 거의 결정됨(`OKBY`가 1개인 유형 다수)
- 지역 선택기 3개(`ncTerrRegion` `ncTerrTarget` `ncTerrLic`) + 최종 확인 "노출 국가"(8320) + 모집 대상 "모집 국가"
- 게시 기간 2곳: "일정 · 검수"(8379) vs "최종 확인 › 게시 방식"(8300)
- 자료 피커 2종: "사용할 IP · 자산"(`ncMatPicks`) vs "자료 · 카탈로그"(배포 자료)
- 예산 2중: 1인 보상 × 인원 자동값 vs `ncBudgetCap` 수동값(12356~12360)
- 주최 프로필 바꾸기 3경로(헤더 피커 · 차단 팝업 · 해시 `ncp`)
- 좌측 레일 라벨 ≠ 본문 앵커 이름("지원 자격 · 선정" ↔ "지원 · 선정", "권리 사용 범위" ↔ "콘텐츠 사용권", "섭외할 크리에이터 조건 / 살 사람 · 빌릴 사람 조건 / 신청자 자격 / 재능 · 전문분야" ↔ 모두 "모집 대상")

### 5-6. 인박스

- 1a(캠페인 묶음)의 핵심은 "머리띠 + 인라인 지원자 행에서 승인/반려"인데 10-01 구현은 머리띠(캠페인 카드)만 반영하고 "지원자 보기"로 이동시킴 → 1a 장점(지원자 탭 안 가도 처리)이 사라짐
- 1a는 "보낸 요청(내 지원)은 묶음 의미 없음"이라고 했지만 **보낸 섭외는 내 캠페인 1개 ← 크리에이터 n명이라 묶음이 의미 있음**. 단점 분석이 보낸 섭외를 놓침
- 계정 중심 인박스인데 프로필 필터는 1b에만 있고 1a · 1c · 10-01 구현에 없음
- 인박스 옵션 문서에 "1a 채택" 문구가 없음(채택은 구두 전언)

## 6. 고도화가 필요한 부분과 제안 (요청 3)

### 6-1. 캠페인 분류 체계 재정의 — 오너 2분류를 살리는 방법

현 체계는 "누가 돈을 내나(EARN/SPEND)" 1축에 세부 12종을 평면 나열. 오너의 "광고 / 프랜차이즈" 2분류는 "무엇을 거래하나(노출·제작 vs 권리)"라는 다른 축. 둘을 합치면:

| 거래 대상(오너 축) | 발주 공고(SPEND, 돈 내는 쪽이 올림) | 판매 공고(EARN, 받는 쪽이 올림) |
|---|---|---|
| **광고 · 제작**(노출 · 결과물) | 홍보(마케팅) · PPL · 퀵오더 · 콜라보 모집 | 크리에이터 서비스(셀프 프로모션) |
| **IP 권리**(사용권 · 소유권) | IP 구매 의뢰 · 사용권 신청 | 사용권 판매(프랜차이즈 라인) · IP판매 |

제안:
1. 데이터 모델을 `category: 'ad' | 'ip_rights'` × `direction: 'spend' | 'earn'` × `subType`(단일 enum) 3필드로 단일화. `CAMPAIGNS.kind` · `kindLabel` · `NC_KINDS` · `ncKind` · `TEMPLATES.kind` 제거
2. "IP 프랜차이즈 캠페인" = `category:'ip_rights', direction:'earn'`의 공식 이름으로 정의하고, **사용권 판매 캠페인(수동)과 라인 자동 생성 캠페인을 하나로 합침**: 프랜차이즈 탭의 라인 = 캠페인의 "권리 조건" 서브 객체. 라인을 만들면 캠페인이 생기고, 캠페인을 열면 라인이 보이는 단일 실체
3. 마켓 입구 3토글(추천 / 일거리 찾기 / 섭외 · 구매하기)은 유지하되 내부 판정은 `direction`으로만. SPEC의 EARN/SPEND 3세대 문단(L634~636, L835~837, L858~860)을 하나로 정리

### 6-2. 활동 프로필(Active Profile) 도입

1. `state.activeProfileId` 1개를 전역으로 두고, 좌하단 전환기가 **이 값을** 바꾸게 함(지금은 프로필 보기로 이동만)
2. 캠페인 만들기 기본 흐름(`ncFlow`) · 지원 프로필 · 섭외 발신 프로필 · 소식 주체 · 자산 소유 · AI 에이전트를 모두 활동 프로필에서 **파생**하고, 모달의 프로필 셀렉트는 "다른 프로필로" 접힌 보조 링크로 격하
3. 활동 프로필 유형에 따라 **처음부터** 허용 흐름만 보이게(브랜드 → 지출형 기본). `ncSnapFlow` 사후 보정 삭제
4. `PROFILES`에 `accountId` 추가, 외부 프로필(hanul 등)은 별도 컬렉션(`EXTERNAL_PROFILES`)으로 분리
5. 같은 계정의 두 프로필이 거래 양쪽인 경우 정책 명시(권장: **차단** — 자기 거래는 수수료 · 에스크로 의미가 없음)

### 6-3. 프랜차이즈 권한 체계 고도화 (핵심)

**현재 상태**: 모델 3개가 섬으로 병존, 어느 것도 계약으로 흐르지 않음.

| 모델 | 위치 | 내용 | 연결 |
|---|---|---|---|
| (a) 38종 권한 | `franchise-rights.html` iframe | 6그룹 · 판매 방식 4종 · 3단 상속 · 대가 6유형 · 194국 3모드 · 슬롯 × 단위 독점 · 검증 V1~V5 | postMessage 0, 저장은 console.log, 프로필 id 미전달(항상 "검은 달의 계약자") |
| (b) 라인 5종 | 메인 하드코딩 `LINES`/`PERSON_LINES`(14536~14547) + `quoteMults`(12150) | 용도 5종 × 지역 7묶음 × 기간 6 × 독점 4 배율 | `LICENSE_LINES` 이름 매칭으로 마켓 노출 on/off |
| (c) 데이터 문자열 | `LICENSE_LINES` · `CAMPAIGN_EXT` · `CONTRACTS.terms` | '아시아 · 3년 · 독점 · 최소보장 ₩5,000,000' 같은 자유 문자열 | 구조화 필드 없음, rightId 없음 |

**제안 — 단일 권리 모델 `RightsOffer` / `RightsGrant`**

```
RightsCatalog (플랫폼 표준)           ← (a)의 38종을 표준 카탈로그로 승격. 그룹 6 → 오너 용도 5종과 매핑표 작성
  id (A-01 …), group, name, specialFields

RightsOffer (IP가 내놓는 조건 = 프랜차이즈 캠페인의 본문)
  profileId, rightId, saleMode(negotiated|instant|creator|off)
  territory { mode: all|only|except, list[] }     ← 3모드 보존, 평탄화 금지
  termMonths, autoRenew { notifyDays, maxRenewals }
  exclusivity { level: none|partial|industry|full, unit: total|region|language|category, slots }
  compensation { type: lump|perUnit|royalty|hybrid, upfront, royaltyPct, royaltyBase: net|gross|unit, mg, reportCycle }
  sublicense { allowed: no|withConsent|yes, revenueShare }
  obligations { startDeadlineMonths, curePeriodDays, credit, fixedClauses[] }
  status: draft|active|paused|soldOut

RightsGrant (체결된 계약 = 조건 스냅샷)
  offerId, offerSnapshot(불변), licenseeProfileId, signedAt, startAt, endAt
  status: pending|active|reporting_due|renewal_due|terminated|reverted
  reports[] { period, revenue, royaltyDue, paidAt }
  approvals[] { derivativeId, state }
```

규칙 제안(지금 비어 있는 것):
1. **독점 충돌 검사**: 같은 `rightId`에 대해 `exclusivity.full` 그랜트의 territory 교집합이 있으면 새 오퍼 발행 · 체결 차단. "SOLD OUT 지역"을 수동 라벨(`slotState.units`) 대신 그랜트 집합에서 **계산**
2. **지역 모델 단일화**: ISO 코드 기반 `WORLD_COUNTRIES` 1벌로 통일. 견적 배율은 7묶음 상수가 아니라 **국가 → 묶음 매핑 테이블**로 계산(190개국 임의 선택도 환산 가능). `USE_COUNTRIES` · `WORLD_REGIONS` · iframe `REGIONS` 폐기
3. **독점 어휘 단일화**: SPEC의 비독점 · 부분 · 업종 · 완전 4단계를 `level`로, iframe의 지역 · 언어 · 카테고리 단위를 `unit`으로 — 둘은 직교하므로 합칠 수 있음
4. **대가 구조 보강**: royalty 단독에도 MG · 리커프먼트 허용, `royaltyBase` 명시, hybrid에 보고 주기 추가, 통화는 오퍼 단위
5. **기간 · 갱신**: 시작일은 계약 체결일 기준 자동 계산, 갱신 통지 기간 · 횟수 · 영구(0) + autoRenew 조합 금지
6. **서브라이선스**: 권리 증명의 "재라이선스 허용" 값(SPEC L236)이 오퍼의 `sublicense` 상한을 **자동으로 잠금**(원권리자 동의 필요 → 오퍼에서 "허용" 선택 불가). SPEC L1010 미결 항목을 이 규칙으로 종결
7. **권리 사슬 매핑**: 프로필 "보유 권리 종류"(저작권 · 상표권 · 영상화권 …)와 38종 권한 사이에 "어떤 보유 권리가 어떤 권한 라인을 열 수 있나" 매핑표(SPEC L243 미리보기 매핑을 확장)
8. **라이선시 화면**: 보유 라이선스 목록(D-day) · 로열티 리포트 제출 · 2차 창작물 승인 요청 · 갱신 요청 · 계약 상세 — 현재 전부 gap. 러닝 로열티는 보고 → 검증 → 정산의 상태 전이를 가짐
9. **계약 효력 1문장 확정**: "확인 체크 = 서명"(현 SPEC)으로 갈지 전자서명(PHASE 2)으로 갈지, 그리고 플랫폼이 계약서를 "제공"하는지 "보관만" 하는지(P-43). 라이선스 · IP판매는 금액이 크므로 법률 검토 필요
10. **활성화 스위치 영향 범위**: 끄면 신규 오퍼 노출만 중단, 기존 그랜트 · 자료 접근은 유지 — 명시
11. **iframe 처리**: (가) 본편에 흡수(권장. 상태를 앱이 소유, 38종은 카탈로그 데이터) 또는 (나) 당분간 유지하되 `postMessage`로 `profileId` 전달 + 저장 payload 수신. 어느 쪽이든 `franchise-rights-setup.html` · `market/ip-detail.html` 등 미존재 링크 정리
12. 비일관 정리: 추천값 `rec`(가격 · 기간 · 슬롯)이 상태에 미반영(FR L1092~1097, A-09 보정 override) · 팟캐스트 B-04/C-05 중복 · A-06 영상화권(일반)과 A-01~03 범위 중첩 · AI 권한 3그룹 분산 · MOQ 2곳 · 영구 + autoRenew · `curePeriodDays` 미저장 · 식별자 충돌(`TERMS` `RIGHTS` `HISTORY`가 iframe과 app-data에서 다른 뜻)

### 6-4. 돈 흐름 단일화

1. 수수료표를 **거래 유형 × 당사자** 1표로 확정하고 플랜별 정산 수수료(12/8/5%)는 폐기 또는 "플랜 할인"으로 재정의. IP판매 · 콜라보 · 서비스 주문 행 추가. 요율은 체결 시점에 계약에 고정 저장
2. 에스크로 시점 1문장: 캠페인은 게시 시 예치 · 체결 시 배정, 서비스 주문은 체결 시 예치 — 이렇게 나눠 쓸 거면 그렇게 명시
3. 예치금 식 1개(`(고정 + 기준 금액) × 인원 × 1.05`), "무제한" 모집은 예치 상한 입력 필수 또는 인원 확정 전 게시 불가
4. 수행자 실수령액(−5%) 표기를 카드 · 상세 · 지원 모달 · 정산에 일괄 적용(SPEC L745 이행)
5. 검수 자동 승인 기한 1개(5영업일 설정형 vs 14일 고정 중 택1)

### 6-5. 상태 머신 명세

현재 상태값이 문자열 자유 텍스트와 수량 혼입. 거래 객체별 enum + 전이표를 SPEC에 추가:

- 캠페인: draft → published(모집 중 | 상시) → paused → closed. (심사 상태 제거 확정 또는 복원 — P-21 결정)
- 지원(Application): submitted → approved | rejected → (approved) contracted
- 섭외(Outreach): pending → accepted | declined | expired | cancelled → (accepted) contracted
- 납품(Delivery): none → submitted → revise(n회) → approved(지급) | rejected
- 계약(Contract): pending_sign → active → in_review → settling → closed | terminated
- 라이선스 그랜트: §6-3
- 배지는 5계열 토큰 상수 1벌(`BADGE.wait/ok/fail/closed/progress`)로만 매핑. 색 변형(#fdf3e8 등) 금지

### 6-6. 캠페인 만들기 단순화

1. 단계 구조 1개로 확정(권장: **3단계 위저드** — ① 무엇을(유형 · 대상 · 제목) ② 조건 · 돈 ③ 확인 · 게시. README "7단계" · `DRAFTS` "5단계" 문구 삭제)
2. 필수값 명시: 제목 · 세부 유형 · 대상 · 금액(지출형) · 게시 설정. 시작일은 "오늘" 기본값
3. 나머지 구획은 "고급 설정" 아코디언으로 접기. 세부 유형별로 보이는 구획 집합을 SPEC 표로 고정(현재 `SECS` 19719~19740의 조건식이 유일한 명세)
4. 중복 통합: 지역 선택기(노출 국가 1개 + 라이선스 사용 지역 1개로 축소) · 게시 기간 1곳 · 자료 피커 1종 · 예산 자동값만(수동 상한은 고급)
5. 좌측 레일 라벨 = 본문 앵커 이름 동일화
6. 게시 성공 시 `CAMPAIGNS`에 실제 추가 → 캠페인 관리 · 마켓 반영(프로토타입 데모 신뢰도)

### 6-7. 셀프 프로모션 · 크리에이터 흐름 확정

**원칙(오너 확인)**: 프로필과 캠페인은 다른 실체. 프로젝트 프로필(IP · Brand · Creator)이 캠페인을 만든다. 이 원칙을 크리에이터에게도 그대로 적용해야 함.

이 원칙에서 보면 SPEC 10-01의 "크리에이터 프로필 저장 → 셀프 프로모션 캠페인 자동 생성 · 프로필이 곧 캠페인 · 캠페인 만들기를 요구하지 않음 · 프로필을 고치면 캠페인도 따라 바뀜"(L1120~1123)은 **폐기 대상**임. 이유:
- 크리에이터만 프로필과 캠페인이 1:1로 묶여 개념 모델이 둘로 갈라짐(IP · 브랜드는 1:N, 크리에이터는 1:1)
- 크리에이터가 성격이 다른 서비스(홍보 · 출연 / 제작 수주 / PPL 출연)를 따로 팔고 싶을 때 캠페인을 나눌 수 없음 → "세부 유형은 캠페인당 하나"(L335) 원칙과도 충돌
- 프로필 편집이 곧 공고 편집이 되어, 공고 상태(모집 중 · 일시 중지 · 종료)와 프로필 상태(공개 · 비공개)가 뒤섞임
- 코드도 이 방향으로 구현되지 않았고(자동 생성 0건), 오히려 저장 후 캠페인 만들기로 보내는 `askOffers` 팝업이 있음

**제안 — 크리에이터도 "프로필 → 캠페인 만들기" 한 경로로 통일**
1. 크리에이터 프로필 = 채널 · 분야 · 포트폴리오 · 가격표(기본값)만 가진 **프로필**. 자체로는 마켓에 "크리에이터 프로필 카드"로만 노출(지원 자격 표시용), 섭외 · 주문의 직접 대상이 아님
2. 크리에이터가 수익형 캠페인(서비스 캠페인)을 **직접 만든다**: 홍보 · 출연 / 제작 수주 / PPL 출연 중 하나를 고르고, 프로필의 채널 · 가격표를 **기본값으로 불러오기**("프로필에서 가져오기" 버튼) 하되 캠페인에서 수정 가능. 09-23에 만든 크리에이터 캠페인 폼(02 재능 → 03 포트폴리오 → 04 서비스 가격표 → 05 일정 · 섭외 조건)을 이 용도로 유지
3. 서비스 주문 · 섭외 제안의 대상은 **공개된 크리에이터 캠페인**. 캠페인이 없는 크리에이터는 지출형 캠페인에 **지원**만 할 수 있음(지원 주체 = 프로필, SPEC L1116 유지)
4. "자동 생성"은 프로필 저장 직후의 **선택 안내**("이 프로필로 첫 서비스 캠페인을 만들까요?")로만 남기고, 캠페인은 사용자가 확인 · 게시해야 생김. 코드의 `askOffers` 팝업이 이미 이 모양이므로 SPEC을 코드에 맞춰 고치는 쪽이 비용이 적음
5. 데이터: `CAMPAIGNS`에 크리에이터 캠페인 N건을 `profileId`로 연결(현재 `ipId` 1:1 가정 제거). `CREATOR_SERVICES`(가격표)는 프로필 기본값과 캠페인 스냅샷 두 층으로 분리
6. 삭제할 SPEC 문장: L1120~1123 자동 생성 4항목, L1122 "캠페인 자동 만들기 버튼도 두지 않는다". 유지할 것: L1116 지원 주체 = 프로필, L1117 "주문은 공개된 캠페인에만"(단 "셀프 프로모션 자동 생성" 수식어 제거)

이렇게 하면 IP · 브랜드 · 크리에이터 셋 모두 "프로필이 캠페인을 만든다" 하나의 모델이 되고, 인박스의 「받은 프로필」 태그 · 캠페인 카드 규격(400px) · 1a 묶음 구조도 크리에이터에게 그대로 적용됨.

### 6-8. 인박스 1a 완성 조건

- 머리띠 아래 지원자 행 펼침 + 인라인 승인/반려(1a의 본질)
- 보낸 요청 탭: 내 지원은 단순 목록, **보낸 섭외는 캠페인 묶음**
